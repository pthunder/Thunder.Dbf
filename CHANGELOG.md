## [0.4.2] - 2026-11-05

The memo guard 0.4.1 added, made whole: a power cut can no longer let a new memo land in the space of one it damaged, in any memo format or open mode, and Jet-maintained dBASE tables work again. Checked on the Windows test PC with real VFP and Jet memo files cut every way, and by a release audit.

**Upgrading from 0.4.1:** nothing in the public API changed. A table whose highest memo was cut by a power cut now refuses writes (`MemoFileDamaged`) whatever its header says; restore its memo file from a backup.

### Changed

- The NuGet packages carry release notes: each version's section of this changelog, shown on nuget.org's Release Notes tab.

### Fixed

- **Gaps in 0.4.1's guard against writing over a power-cut memo.** Each let a new memo land in the space of one the cut damaged, so the old memo read back with the new one's bytes in it:
  - **Tables opened from streams** (`DbfTable.Open(stream, memoStream: …)`) skipped the guard. They now refuse writes too. Like every table opened from streams, they aren't padded.
  - **A memo file cut below its 512-byte header** counted as one with no memos yet, even when records named blocks in it. It's now checked like any other short memo file.
  - **A dBASE III memo cut mid-text** read as shorter text, since it has an end marker but no length, so it counted as whole. Writes stayed on, and an exclusive open even padded over it. It now counts as cut.
  - **A dBASE III record with two memos**, the first cut and the second whole: reading the second hid the first.
  - **A header that lost its new end.** A cut can take a memo's tail and the header's updated next-free block with it, so the old header names an end inside the file. A dBASE IV memo file can show the same thing when a cut takes the last link of its chain of free blocks. For every memo format, the highest memo any record names is now checked to lie whole in the file. The block numbers are read straight from the records, ASCII or binary, skipping fields marked .NULL., and only one memo is read.

  In each case, writes to the table are refused (`MemoFileDamaged`) and `Check()` says to restore the memo file from a backup. 0.4.0 had no guard at all.
- **`Check()` no longer calls Jet-maintained dBASE memo files damaged.** Jet doesn't pad a `.dbt`'s last block, so the file ends before the block its header names. 0.4.1's `Check()` reported that as a power cut, quoting Visual FoxPro's error 41, after every Jet write, and an exclusive open padded the file each time. A `.dbt` whose memos are all whole is now left alone. A `.fpt` is still reported and padded, since Visual FoxPro needs that.
- **A dBASE IV memo header a cut rolled back** points at a used memo block. That block's marker was read as a free-chain link, so `Check()` named a shortfall of hundreds of megabytes. It now says the memo runs past the end of the file.
- **A dBASE IV append no longer writes over a memo a rolled-back header names.** A cut can keep a memo whole and lose only the header's new end, which then names that memo's block. The append's walk of the free chain took the memo's marker for a link and wrote over it. A link to a used block now counts as stale and is pointed at the new end.
- **A healthy table whose highest memo is over 64 MiB** (Visual FoxPro allows that) no longer counts as cut. Whether the highest memo lies whole is now worked out from its stored length or its end marker, without loading it.
- **Memos can be added to dBASE IV tables whose memos Jet rewrote.** Jet links freed blocks onto the head of the free chain, so its chain runs downward. Since 0.4.0, Thunder.Dbf took any link that went down for damage and threw `InvalidDataException` on every memo write, while `Check()` called the table clean. The chain is now followed in any order. A chain that really loops is reported by `Check()` and refuses memo writes with `MemoFileDamaged`, before a byte is written.
- **A dBASE IV append that grows a file a cut left short** no longer writes over its own text. After writing the memo, the chain walk ran over the grown file, so a stale link that pointed inside the new memo took four bytes of its text as a link and overwrote them. The walk now stops at the file's old end.
- **Writable opens of a memo file that ends early no longer read every memo.** Only the highest memo a record names is read, since memos don't overlap. On a Jet-maintained table, that was every writable open.

## [0.4.1] - 2026-11-05

Compatibility with Jet and Visual FoxPro, found by testing 0.4.0 against them on Windows: Jet finds every record in a dBASE `.mdx` Thunder.Dbf writes, VFP datetimes read as VFP means them, and kills and power cuts that 0.4.0 left silently wrong are now reported or repaired. Checked on the Windows test PC with VFP 9, Jet, killed writers and Hyper-V power cuts, and by a release audit.

**Upgrading from 0.4.0:** nothing in the public API was removed, and code compiled against 0.4.0 runs unchanged. Things to know:
- If 0.4.0 or earlier wrote to a dBASE `.mdx` table that Jet or Access also reads, run `RebuildIndex()` once (the table opened `exclusive: true`). Until then Jet can still miss records whose keys 0.4.0 wrote.
- A writable open now refuses writes (`IndexDamaged`) to a table whose `.mdx` doesn't match it, as it already did for a `.cdx`. `RebuildIndex()` clears it.
- A `.cdx` tag on a Visual FoxPro datetime field reports `KeyType` `'T'`, not `'D'`, and its keys come back as `DateTime`.

### Fixed

- **Jet could miss live records in a dBASE `.mdx` number tag** that Thunder.Dbf had written to. This affects 0.2.0 to 0.4.0. Jet compares key bytes when it steps from one match to the next, and goes down the tree by interior keys without moving on to the next leaf. On the Windows test PC, 2,000 ordinary writes left Jet missing 46 of 9,210 live IDs. Thunder.Dbf's own lookups, `Check()` and its rebuild comparison compare keys by value, so they saw nothing wrong. There were two causes:
  - **Digit counts.** Each number key stores a digit count. Jet counts 10 for a whole number and the significant digits otherwise. dBASE counts the significant digits. Thunder.Dbf counted the digits it printed (Xbase64's rule). It now follows the tag's writer, read from its first and last leaf. Tags that don't show one, including new tags and tags 0.4.0 wrote, use Jet's rule. Values and their order don't change, and Thunder.Dbf reads keys in any form.
  - **Interior keys.** When a leaf's last key moved out, the key above it stayed where it was, too high, and Jet then missed keys in the next leaf. Interior keys now always equal their child's last key, as dBASE and Jet keep them. A new key equal to an interior key goes into the child that key covers.
  - **If 0.4.0 or earlier has written to a table that Jet or Access also reads,** run `RebuildIndex()` once after upgrading. It puts every key into Jet's form, and Jet then finds every record.
- **Visual FoxPro datetimes read a second early.** VFP often stores a whole second a millisecond short (03:42:47 as 13,366,999 ms), and VFP and its OLE DB provider read it as the second it meant. Thunder.Dbf now does the same: a time within a millisecond of a whole second reads as that second, so 23:59:59.999 reads as the next midnight. Any other time keeps its milliseconds. VFP itself has whole seconds only and rounds half up, so a time Thunder.Dbf writes as 08:00:00.500 reads with its .500 here and as 08:00:01 in VFP.
- **A `.cdx` tag on a datetime field seeks and reads with its time.** It used to act as a date tag, so `SeekExact` with a `DateTime` found nothing and `Entries()` returned dates. Its `KeyType` is now `'T'`. The keys written were already right; LINQ queries still scan such a field.
- **An `.mdx` with a key too many or too few is caught.** A writer killed between the table and the index can leave one, and so can Jet writing beside another program. A writable open now checks, as it does for a `.cdx`, that each tag holds one key per record and has the last two records' keys. Keys are counted from the index's leaves without being read: about 70 ms for a million records in three tags. If a check fails, writes stop with `IndexDamaged` until `RebuildIndex()`, and `Check()` reports it as a problem. `Check()` also checks that each UNIQUE tag holds one key per distinct value. On the Windows test PC, 12 of 30 kills had left one that went unnoticed.
- **A memo file shorter than its header says is repaired.** A power cut can keep the `.fpt` or `.dbt` header's new end and lose the blocks before it. Visual FoxPro then refuses the table (error 41). `Check()` now reports it, and when every memo a record names still reads whole, an exclusive writable open pads the file back to its full length. If the lost tail took part of a memo, the file is left as it is, writes to the table are refused (`MemoFileDamaged`), and `Check()` says to restore it: padding, or a new memo written where the lost end was, would make that memo read back with other bytes in place of its text.
- **Finishing a journal note 0.4.0 left could remove the record's own number key.** The note holds 0.4.0's keys and the record's key is now in Jet's form, and the two were compared byte for byte, so the record's own key looked like the cut-off change's old one. They're now compared as the index compares them, by value. On the Windows test PC, 6 of 30 of 0.4.0's journal kills lost a key this way.
- The tests that create symbolic links are skipped, not failed, on a machine that can't create links (Windows without Developer Mode or administrator rights).

### Changed

- **Writes to an `.mdx` table opened `exclusive: true` are about 2.5 times faster.** Each indexed update took about 50 µs and now takes 20. No other program can open the table then, so a write no longer reads the `.mdx` tag table again first. Creating or dropping a tag still reloads it.

### Added

- `samples/Maui`: an iPhone CRM built with .NET MAUI. It opens any dBASE or FoxPro table from Files, with its memo and index files, and works out which fields hold the name, phone, follow-up date and so on from their names. Edits keep the `.cdx` or `.mdx` index up to date, and Share sends the files back out in their original format. Tested on the iOS 27 simulator.

### Tests

- **The Visual FoxPro round-trip test covers FoxPro writing added since 0.2.0:** tables made by `DbfTable.Create` in both FoxPro formats, a `.cdx` made by `CreateIndexTag`, appends without a `_NullFlags` value, and `ModifyStructure` with `DropIndexTag`. VFP lists every value and must read what Thunder.Dbf reads. They haven't run against VFP yet; the [checklist](docs/maintainers/visual-foxpro-test.md) says how.

## [0.4.0] - 2026-11-03

Changing a table's structure (preview), dBASE `.mdx` splits that keep their keys through a killed writer and keep their order through a power cut, and a library that trims and compiles ahead of time for iOS and Android. Checked by four release audits before shipping.

**Upgrading from 0.3.1:** nothing in the public API was removed or changed, and code compiled against 0.3.1 runs unchanged. Behavior changes to know about:
- With `FlushWritesToDisk` on (the default), each `.mdx` node split now waits for the disk between its steps, so `AppendRange` of 100 records into an indexed dBASE table took about 90 ms instead of 16. A `DeferIndexWrites` batch under `LockTable()` saves them in about 23 ms.
- Opening a table writable checks for a structure change left unfinished by a crash, and finishes or undoes it first. With nothing to finish, this cost about 1 ms per writable open in the benchmarks (open, update 100 records, close: 6.9–7.6 ms against 5.6–6.4 ms); reads and writes once a table is open are as fast as in 0.3.1.
- `ModifyStructure`, `AddField`, `DropField`, `AlterField` and `DropIndexTag` are new and marked `[Experimental("THDBF001")]`: calling them needs `#pragma warning disable THDBF001` (or `<NoWarn>`), as a reminder to back up tables you can't afford to lose first.

### What's new and fixed

- **A power cut while a dBASE `.mdx` node splits keeps the steps in order,** when writes are forced (`FlushWritesToDisk`, the default). The split's steps were written in a safe order but not forced between them, so a disk could put the shortened node down before the parent that points past it (found by an automated release audit). Each step is now on disk before the next one depends on it. This orders whole writes; it doesn't make one node's write all-or-nothing. A disk that keeps only part of a 1 KB node write (one sector of two) can still leave that node damaged, as before, and `RebuildIndex()` is the way back. Tested by replaying every mix of unflushed writes at every point an insert could lose power; with the flushes off, keys go missing. With flushes on, saving 100 records with `AppendRange` now takes about 90 ms instead of 16 ms; a `DeferIndexWrites` batch saves them in about 23 ms. Nothing changes with flushes off or inside a batch.
- **A writer killed while a dBASE `.mdx` node splits no longer loses keys already in the tag** (#35). A split used to write the shortened node before linking in its new right half, so a cut between the two left up to half a node of keys unreachable, silently. Now the new nodes go first, then the tag header if the root moved, then the changed nodes from the top down. A cut at any point leaves every old key findable (a scan may see some twice); one inside an interior split can leave a page reached through both halves, which the index reports as damaged and `RebuildIndex()` repairs. Tested by cutting an insert off after each of its writes in turn, for a root leaf, a leaf under an interior root, and a split that reaches an interior node.
- **Splits no longer re-read and decode the path.** A full leaf splits using the nodes the search already read on its way down, instead of reading the path from the root again into lists with one array per key: 20% less allocated in a 100,000-row load with 2 tags, and a few percent faster. The `.mdx` files written are byte for byte the same as before.
- **Safe to trim and compile ahead of time,** as iOS requires and Android allows (.NET MAUI, Native AOT). `Thunder.Dbf` is marked `IsAotCompatible`, so the trim and AOT analyzers check its build, which fails on the warnings for unannotated reflection, calls to members that need unreferenced or dynamic code, and annotations that don't match (the list is in `Thunder.Dbf.csproj`). CI publishes the new [NativeAot sample](samples/NativeAot) with `PublishAot=true` on Linux and macOS, warnings as errors, and runs it: create, append, index, seek and read a table in code page 866, typed records and ADO.NET. It used to give 10 trim and AOT warnings, all from three reflection-based features:
  - Typed records (`Read<T>`, `ReadAll<T>`, `AppendRecord`, `UpdateRecord`) mark `T` with `[DynamicallyAccessedMembers]`, so a trimmed app keeps the class's public properties and constructor. A blank field read into a non-nullable value-type property is made as before, with the struct's own parameterless constructor when it has one; a trimmed app keeps that constructor only if something asks for it (a `[DynamicDependency]`), and otherwise reads the zeroed value instead of failing.
  - `AsQueryable<T>()` is marked `[RequiresUnreferencedCode]` and `[RequiresDynamicCode]`, since LINQ's queryable operators find their in-memory versions by reflection: a trimmed or AOT app's build now warns, pointing at `ReadAll<T>()`, `Read(index)` and `Seek`. Nothing changes for other apps.
  - `DbfDataReader.GetFieldType` carries the same annotation as `DbDataReader`'s.
  `Thunder.Dbf.Sql` has no trim or AOT warnings of its own; whether it runs trimmed depends on the ADO.NET provider it's given. [Getting started](docs/getting-started.md#mobile-and-aot) has a short Mobile and AOT section, including that tables in the app's own folder are deleted on uninstall, as an SQLite database there is.
- **Changing a table's structure (preview):** `table.ModifyStructure(fields)`, like dBASE's and FoxPro's `MODIFY STRUCTURE`, adds, drops, renames, widens, narrows and retypes fields in all four formats, with `AddField`, `DropField` and `AlterField` for one field and `FieldDefinitions` to start from. It writes a new table beside the old one, carries every record across (deleted ones still deleted, in the same order) with values converted where the types allow, copies the memo file whole, rebuilds the `.mdx` or `.cdx` with the same tags, and only then swaps the new files in, keeping the old ones in `NAME.DBF.restructured-<time>` (`StructureBackupPath`). A change that would lose a value is refused unless `allowLoss: true`; a tag over a dropped or renamed field is refused. Visual FoxPro nulls, autoincrement counters and binary (NOCPTRANS) fields carry across, and tables in a database container are refused. The swap is a transaction, its steps listed in [the protocol](docs/formats/restructure.md): the backup folder holds its lock, a manifest naming every file that moves, and a decision published by a rename; each file moves in two renames (old into the backup, new into place). A process killed at any of those steps, the change's or an exclusive open's finishing it, leaves the next exclusive open to finish the change once its decision is published, and before that to undo it, putting back every file the backup holds and taking back any the change added, so the old table is byte for byte as it was; even the `.dbf` itself between its two renames is found, by `DbfDatabase` too. A power cut can do less well: see [Durability](docs/durability.md). A failure before the decision undoes the change and says why; one after it says the change is decided and waits for the next exclusive open. While a change is under way Thunder.Dbf writers are turned away, and on Linux and macOS (64-bit processes; on Linux, glibc 2.33 or later or musl) every open checks by device and inode that the `.dbf` it opened is the one now at the path, so a handle opened just before the swap is reopened rather than left writing into the backup; elsewhere there's no such check, so keep other Thunder.Dbf writers away while a structure changes. Numbers are checked against the value itself, so a double too small or too precise for the new field is a loss; a blank stays blank in a nullable field, and a blank number going into an integer, double or currency field (which have no blank, only 0) is a loss too. The new files keep the old ones' Unix permissions. This and `DropIndexTag` are a preview: they're marked `[Experimental("THDBF001")]`, so calling them is a build error until you suppress THDBF001, and you should back up tables you can't afford to lose before using them. It returns the reopened table and closes the one it was called on. It rewrites the whole table, so it takes time and disk space in proportion to it (figures in [Reading and writing](docs/reading-and-writing.md#it-rewrites-the-whole-table)).
- **`DropIndexTag(name)` (preview, THDBF001),** like `DELETE TAG`, takes a tag out of the production `.mdx` or a FoxPro table's structural `.cdx`; a `.cdx` tag's pages go on the free list for FoxPro to reuse. An `.mdx` loses its tag in three writes that each leave dBASE's tag-name tree finding every other tag. Cut off after the first, the table still counts its last slot, which holds what it held before: the last tag again (Thunder.Dbf reads it once, but a program walking the slots rather than the tree lists it twice), or the dropped tag itself when that was the last. Before the first of them, a copy of the header and tag table is written with its SHA-256 under a temporary name, forced to disk and renamed `NAME.MDX.droptag`, since a power cut can tear those writes sector by sector. The next writable exclusive open writes the copy back (the tag isn't dropped after all) once its hash checks out, and refuses with `IndexDamaged` when it doesn't. Until then Thunder.Dbf doesn't use the index: `MdxIndex.Open`, a shared writable open, and the table that tried the drop all refuse with `IncompleteTransaction`. dBASE and other programs don't know the file, and read the tag table as it is.
- `DbfFieldDefinition.Binary` creates Visual FoxPro character and memo fields marked NOCPTRANS.
- `DbfErrorCode.WriteFailed`: a file couldn't be written, moved or deleted for a reason the other codes don't name (a full disk, a failed device or share).

## [0.3.1] - 2026-11-03

A fix for the first thing a new user of 0.3.0's Visual FoxPro tables hit, and the web service's sign-in packages on one version. Nothing in the public API changed; code compiled against 0.3.0 runs unchanged.

- **`Append`, `AppendRange` and `Update` take one value per field the table was created with,** on a Visual FoxPro table with nullable fields too: its hidden `_NullFlags` is worked out from the others. They used to want a value for it as well, so `Append(1, "Ada")` on a table with two fields, one of them nullable, failed with "The table has 3 fields but 2 values were given" (found by the 0.3.0 smoke test). A value for `_NullFlags` is still accepted, so existing code runs unchanged, and the error for any other count now says the hidden field needs no value. `DbfRecord.Values` still lists `_NullFlags`.
- **The web service's IdentityModel packages are all 8.23.0.** The 0.3.0 update raised `System.IdentityModel.Tokens.Jwt` alone, leaving the OpenID Connect packages that `JwtBearer` brings in at 8.19.2; Microsoft asks for one version across them, since a mix can fail at run time. This affects the `thunder-dbf-server` downloads only, not the NuGet packages.

## [0.3.0] - 2026-11-03

New tables in any of the four formats, and dBASE `.mdx` writes about twice as fast, with bulk loads batched as FoxPro's already were.

**Upgrading from 0.2.0:** nothing in the public API was removed or changed, and code compiled against 0.2.0 runs unchanged. Behavior changes only where `DeferIndexWrites` is set on a dBASE table (one with an `.mdx`), where it used to do nothing:
- Under `LockTable()`, the `.mdx` changes wait until the lock is disposed. Until then dBASE readers, and an index opened separately in the same process (`OpenProductionIndex()`), see the batch's records with the index as it was before the batch: a seek for a key the batch added misses it.
- The batch is noted in `TABLE.DBF.journal` beside the table, so the folder must let it be created, and the batch is forced to disk when it ends, whatever `FlushWritesToDisk` says.
- Every page the batch changes stays in memory until it ends.

Leave `DeferIndexWrites` off where a write must show in the index straight away; `AppendRange` suits small groups.

### What's new and fixed

- **New tables in any format:** `DbfTable.Create(path, DbfTableFormat.VisualFoxPro, fields)` (also `DbaseIII`, `DbaseIV`, the default, and `FoxPro2`) writes the matching header and memo file (`.dbt` or `.fpt`). Visual FoxPro tables get integer, currency, double and datetime fields (`DbfFieldDefinition.Integer`, `Currency`, `Double`, `DateTime`), `Nullable` fields with the hidden `_NullFlags`, and `AutoIncrement` integers, with field flags as Visual FoxPro 9 writes them. CSV import takes `Format` too (its `LanguageDriver` then defaults to the format's Windows-1252 mark, and `Overrides` can use the Visual FoxPro types), and `thunder-dbf import` takes `--format dbase3|dbase4|foxpro2|vfp`.
- Setting an empty nullable field to null with `UpdateFields` now writes the null.
- **`DeferIndexWrites` covers dBASE `.mdx` indexes too:** under `LockTable()`, a batch keeps the `.mdx`'s pages in memory and writes each changed one once, when the lock is disposed: new blocks first, then the tree blocks that existed, then the tag headers that point at each root, then freed blocks, and the file header last. It has the same journal note as a `.cdx` batch, and the same refusal until `RebuildIndex()` if it's cut off. A batch reloads the tags and reads the file afresh when it starts, so another writer's changes since this process last looked aren't lost to read-ahead (found by an automated review).
- **Faster, leaner `.mdx` writes:** a key that fits in its leaf is added in place, in a reused buffer, and the nodes above it are no longer decoded into new arrays on the way down. A unique tag's check for a taken key reads the same way, and a key that sorts after every other (IDs added in order) no longer walks the tree for it. Only the root pointer and has-keys flag are read from a tag's header, and the table's `.mdx` is opened unbuffered, like the `.cdx`: every read used to flush a 4 KB buffer and read 4 KB to use one block. Loading 100,000 rows into a table with 2 tags under `LockTable()` with `DeferIndexWrites` took 2.8 s and allocated 3.4 GB with 0.2.0, and takes 1.3 s and 490 MB now; opening a 5,000-record table, adding 100 records one at a time and closing it went from 4.8 ms to 4.0 ms (macOS, Apple silicon, the same run). The `.mdx` files written are byte for byte the same as 0.2.0's, with and without a batch.
- **`RebuildIndex()` repairs an `.mdx` tag that reaches a page twice,** as a batch cut off while its pages were going out could leave one. It used to refuse ("reaches index page N twice"), leaving no way back but by hand. The damaged tree's pages aren't freed, since dBASE reuses freed pages and they can't be trusted to be that tag's (found by an automated review).

## [0.2.0] - 2026-11-01

Checked against Visual FoxPro 9 itself on Windows: its own tables and indexes in eleven code pages, Thunder.Dbf and VFP writing the same files at once, writers killed mid-write and 150 Hyper-V power cuts. Thunder.Dbf was never silently wrong: what a kill or a cut left was always either clean or reported. Visual FoxPro and its OLE DB driver, killed 180 times mid-write, left 51 tables silently wrong. FoxPro `.cdx` maintenance is still opt-in (`maintainFoxProIndexes`).

**Upgrading from 0.1.0:** nothing in the public API was removed, and code compiled against 0.1.0 runs unchanged. Two behaviors changed:
- `Pack()`, `RebuildIndex()`, `CreateIndexTag()` and `MaintainIndex(path, rebuild: true)` need the table opened with `exclusive: true`, as in dBASE and FoxPro; they throw `ExclusiveUseRequired` otherwise.
- `DbfTable.Create` holds the new `.dbf` unshared while it's open.

### What's new and fixed

- **Counted records that were never written are found too:** a power cut can leave a file long enough for every counted record whose last ones were never written (an end-of-file mark on a record boundary, then zeros to the end of the disk page). Only records starting with a deletion flag count, so these are reported and cut back like a short file instead of being kept as blank records. A moot batch note is cleared at the exclusive open, not only at the first write.
- **A header counting records the file doesn't hold is reported and repaired:** a power cut can keep the count and lose the last records (4 of 50 Hyper-V cuts with flushes off). `Check()` now reports it as a problem (it said "No problems"), and a writable exclusive open cuts the count back to the whole records the file holds, keeping a part record's bytes beside the table, reporting the number in `RecordsMissingFromFile`, and rebuilding the indexes (the structural `.cdx` is taken over again where it can be). There used to be no way back but by hand. A cut-off batch's journal note whose indexes have all been deleted is now cleared instead of refusing writes for ever.
- **`UPPER()` in `.cdx` keys over letters beyond ASCII,** in code pages 437, 850, 852, 866, 1250, 1251, 1252, 1253, 1254 and 1257 (Western, Central European, Cyrillic, Greek, Turkish and Baltic, Windows and DOS), where case-insensitive name tags are common: upper-cased as Visual FoxPro 9 SP2 does, measured for every byte against VFP running in each code page (.NET's capital when the code page has it, the byte kept when it doesn't, as for µ, and VFP's own result for the few bytes where it differs, such as ž in 1252). In 852, 1250 and 1251, VFP's SEEK and REINDEX were checked on tags Thunder.Dbf built and kept. Other code pages keep refusing such keys until they're measured the same way.
- **A deferred batch's pages and records are forced to disk before its journal note is emptied,** whatever `FlushWritesToDisk` says (one flush per batch). With flushes off, a power cut could keep the emptied note and lose the batch (3 of 50 Hyper-V power cuts; Thunder.Dbf still refused all three tables, by their key counts).
- **`RebuildIndex()` takes over a structural `.cdx` that was refused when the table opened** (keys out of step with the table, after a batch was cut off, say) and rebuilds it with the rest, as `MaintainIndex(path, rebuild: true)` does; it used to say "no index open" (found by the Visual FoxPro kill tests).
- **Fuzzed:** `tools/Thunder.Dbf.Fuzz` throws corrupted copies of the test files at every reader and writer. 100,000 cases found no crash, hang or runaway allocation, and six places where a damaged file gave a raw .NET exception instead of an explained one, all fixed with tests (`FuzzRegressionTests`): a table cut short (`EndOfStreamException` while reading, now `NotADbfFile`); a header counting more than 2^31 records (`OverflowException`); an index entry pointing past the table's end in `Seek` and `ReadInOrder` (`ArgumentOutOfRangeException`, now `IndexDamaged`); an index key expression that doesn't parse or fit the table, met while writing (now `IndexDamaged`); a numeric `.mdx` key whose digits aren't BCD; and the autoincrement flag on a field that isn't Integer, which Visual FoxPro never sets (now ignored).
- **Faster deferred batches:** inside a `DeferIndexWrites` batch the `.cdx` node cache shares its nodes instead of copying them in and out (the copies were most of a 7-tag batch's time on Windows), and each record's planned key changes are sized up front.
- **`DeferIndexWrites`, for migrations and bulk loads:** with it on, a batch under `LockTable()` keeps its `.cdx` changes in memory and writes each changed page once, when the lock is disposed. It holds the index lock meanwhile (Visual FoxPro users wait), and the batch is noted in the table's journal until its pages are written, so a batch cut off (killed, or a failed write) stops Thunder.Dbf writes until `RebuildIndex()`, updates included. Off by default; ignored while `UseJournal` is on. `docs/durability.md` has a table of what each setting trades.
- **Faster `.cdx` writes on Windows:** a writable table watches its folder for new files instead of checking the folder before every write (other systems, and a watcher that fails, keep the folder-time check). Notice of a new file comes a few milliseconds after it appears, so a write within those milliseconds doesn't see it; the next one does.
- **A FoxPro tag whose keys would be longer than 240 bytes is refused** with `InvalidValue` before anything is written. It used to fail with an `InvalidDataException` from inside the tree code (found by the Visual FoxPro stress tests; nothing was damaged).
- **Faster `.cdx` writes, again:** while a `.cdx` is exactly as this process last left it (same length and update counter), its tree pages come from memory instead of the file, and the `.cdx` is read and written unbuffered, so a page read no longer pushes out buffered writes first. Another program's change (Visual FoxPro's own, included), a failed change or a reload empties the cache. On a Mac with flushes off, appends to a 7-tag table went from about 10,000 a second to 14,500.
- **Faster writes.** `FlushWritesToDisk` (on by default; `DbfDatabaseOptions.FlushWritesToDisk`, `Flush Writes To Disk=false`) turns off the forced disk flushes behind every write, keeping their order, so a killed process is still covered and only a power cut or operating-system crash can lose the latest writes (as with Visual FoxPro). PACK always forces its writes, and so does every write while the journal is on. Whatever the setting, a `.cdx` that's exactly as this process left it (same length and update counter) is no longer reloaded and re-parsed before every write, one record's changes to a `.cdx` share one index lock, and the folder isn't listed for new index files, an unfinished PACK or a journal on every write, only when the folder changes (or once a second; a table keeping a journal looks every time). On a Mac with flushes off, 2,000 appends went from about 5,500 a second to 14,500 (a 2-tag table) and from 5,000 to 10,000 (7 tags).
- **Records an interrupted append left past the count are kept, not just removed:** before a writable exclusive open takes them off, their bytes go to `TABLE.DBF.cutoff-<UTC time>` beside the table (a new name each time; delete it once nothing in it is wanted), and `CutOffRecordsRemoved` and `CutOffBackupPath` report it (review of #13).
- **The journal holds keys up to 256 bytes** (Clipper's `.ntx` limit; it stopped at 240, so a cut-off write on a table with longer `.ntx` keys left a note that stopped writes), and refuses a longer key when it writes the note (review of #17).
- **The journal reader checks every count and length** against the note it reads; a whole note that doesn't make sense (damaged, or not written by Thunder.Dbf) stops writes with an explanation until a rebuild, instead of failing with an out-of-range error. Index and tag names a note holds go in the error's `Diagnostic`, not its message (review of #14).
- Lock calls that need a shorter wait (the open-time `.cdx` check, finishing a journal note) pass it per call instead of changing the table's `LockTimeout` for a moment.
- **Behavior change:** `DbfTable.Create` holds the new `.dbf` unshared while the table is open (other programs can't open it until it's closed), so `INDEX ON` and `PACK` can follow straight away.
- `Check()`'s summary says "No problems; N note(s) below." when tables only have notes (such as a missing code page), instead of "All good." above a warning.

### Engine (Thunder.Dbf)

FoxPro `.cdx`/`.idx` maintenance (still the opt-in `MaintainFoxProIndexes` preview) is safer:

- **PACK, rebuilds and INDEX ON need exclusive use,** as they do in dBASE and FoxPro: `Pack()`, `RebuildIndex()`, `CreateIndexTag()` and `MaintainIndex(path, rebuild: true)` throw `ExclusiveUseRequired` unless the table was opened with `DbfTable.Open(path, writable: true, exclusive: true)` (`DbfDatabaseOptions.Exclusive`, `Exclusive=true` in a connection string). An exclusive open fails with `FileInUse` while another program has the table open. Run against a table Visual FoxPro had open shared, a rebuild left VFP reading freed pages (error 2066, "tag is corrupted") and a PACK renumbered records under it (found by the Visual FoxPro tests). **Breaking:** code that packs or rebuilds must open the table exclusively.
- **Creating FoxPro `.cdx` tags:** on a FoxPro or Visual FoxPro table, `CreateIndexTag` adds a tag to the structural `.cdx` (creating it, and flagging it in the table's header, when there's none), like VFP's `INDEX ON ... TAG`, with UNIQUE, CANDIDATE (a new overload), FOR and DESCENDING. Tags are laid out as Visual FoxPro 9 lays them out and hold the keys VFP's own `INDEX ON` gives: every kind of tag in a VFP-built table, made again here, matches VFP's key for key. Needs exclusive use and `maintainFoxProIndexes`.
- **`.cdx` keys over currency, datetime and nullable fields** (a bare field) are kept, built byte for byte as Visual FoxPro 9 builds them; they used to be refused. Leaves are packed as VFP 9 packs them (a shared prefix stops at the previous key's trailing blanks).
- **Crash-safe key changes:** an update, delete or recall now writes the new keys, then the record, then removes the old keys, each on disk before the next, so a writer killed between steps leaves an extra key, never a missing one (UNIQUE tags, where a key belongs to one record, still change after the record). The Visual FoxPro kill tests found 7 in 60 killed updates leaving a record its new key couldn't find. Opt-in **journal**: `UseJournal = true` (`DbfDatabaseOptions.Journal`, `Journal=true`) notes each such key change, and each batch of appends, in `TABLE.DBF.journal` first, and the next write, shared or not, in any Thunder.Dbf process keeping the same indexes, finishes one that was cut off: the index ends up exact, UNIQUE tags included, and an append cut off before its count is taken back off (the Visual FoxPro kill tests found it came back as error 2091 when the next writer wasn't exclusive).
- **Attaching a Clipper `.ntx` while Harbour or Clipper programs write** walks its key order under Clipper's index lock, so a page caught mid-change isn't taken for keys out of order.
- **`FIELD->NAME` in index keys and expressions** (and Harbour's `_FIELD->NAME`) means the table's own field, as in Clipper and Harbour; it was refused as another work area (found with a Harbour-built `.ntx`).
- **A `Jet` lock scheme for tables Access shares:** Microsoft's Jet and ACE read a held dBASE header byte (4,026,531,838) as an exclusive open and fail at once, so with the dBASE scheme every Thunder.Dbf append and update gave Jet users "already opened exclusively" errors (1,580 in 15 seconds with 8 Jet users in the Windows tests). `LockScheme = DbfLockScheme.Jet` (`Lock Scheme=Jet`) makes header changes under the append byte, which Jet itself takes to append, for Access or Jet **reading** while Thunder.Dbf writes. Jet mustn't write while anything else writes, not even another Jet program: it takes no lock on the `.mdx` and tears it (the Windows tests saw it with two Jet processes and nothing else), which the locking docs now say. `Auto` still picks dBASE, which the Borland Database Engine (GoldMine) is assumed to use.
- `LockScheme` can be changed whenever the table holds no lock, not only before its first lock.
- **Interrupted appends are cleaned up:** records left past the header's count by an append that was cut off (Visual FoxPro calls the table corrupted, error 2091) are reported by `Check()` and taken off, with the indexes rebuilt, when the table is opened `writable: true, exclusive: true`. Shared writers leave them, since they can't be told from another program's append in progress. Only bytes that look like whole records are touched, and only when every index next to the table is kept or can be taken over with a rebuild, so no key is left pointing at the next record appended there.
- **The open-time `.cdx` check is safe next to Visual FoxPro:** it walks the tree without VFP's index lock, then confirms, under the table's header lock (which VFP holds through an append) and the index lock, that the update counter and the record count didn't move, and repeats if they did, so another program's append in progress isn't taken for damage. On a table other users never stop writing to, it walks under those locks after two tries, waits at most a quarter of a second for each, and if they're still busy leaves the full check to the first write, which holds them anyway (found in a multi-user Visual FoxPro test, where a 7-tag table never held still); an index that still looks out of step gets about a second to settle. It also checks that the last records have their keys in every non-UNIQUE tag that includes them, FOR tags among them.
- **A tag short of the table is caught on open:** a tag with no FOR filter and no UNIQUE must hold one key per record, so a different count (a writer killed between writing a record and its keys) now refuses the index, with the reason in the error's `Diagnostic`, instead of taking it as it is. On a table opened exclusively, `MaintainIndex(path, rebuild: true)` takes over and rebuilds such an index, or one whose keys are otherwise out of step with the table (found by the Visual FoxPro tests: 2 of 20 killed writers left a tag one key short).
- **Tag roots stay put:** a full root's keys move down into new pages and the root is rewritten in place; shrinking and rebuilds also keep the root's address. Visual FoxPro reads each root's address once, when it opens the table, so a moved root left it walking a stale page while Thunder.Dbf wrote (found by the Visual FoxPro round-trip test).

- **Visual FoxPro's index lock:** every change, and every reload of the tag list, runs under the lock Visual FoxPro takes on the index file itself (one byte at 0x7FFFFFFE), following `LockTimeout` and `RequireLocks`; pages are re-read under it and the update counter is bumped before it's released.
- **Crash-safe page order:** splits write the new page before the page that links it in, emptied pages go on the free list only once nothing points at them, and a rebuild builds a whole new tree and switches to it in one header write. A crash can leave keys listed twice or unused pages, never a key missing.
- **Visual FoxPro's UNIQUE tags** change the way Visual FoxPro changes them between rebuilds: the first record with a key keeps it, and nothing is promoted when it leaves. A rebuild still picks the lowest record.
- **Candidate keys** are checked against every key an `AppendRange` batch has planned, so two equal keys in one batch are refused; a rebuild checks its keys among themselves.
- **Keys built byte for byte:** character keys come from the stored field bytes (a field holding `A\0` keys as FoxPro keys it), and leaves pack record numbers past 67,108,863 the way Harbour and FoxPro do, for both reading and writing.
- **Refused rather than guessed:** `.cdx` files whose pages have two owners or one-way sibling links (as damaged); numeric keys over more than a bare field; character keys built with functions other than `UPPER`, `DTOS` and `STR` of fields; `UPPER` and text FOR filters in double-byte code pages.
- **Takeovers:** `MaintainIndex(path, rebuild: true)` takes over a tag out of byte order anywhere (the root included), rebuilds an index that's already kept, and lets the index go again if the rebuild fails.
- **FoxPro 2 detection:** a version-0x03 table with the index flag, no `.mdx` and a same-named `.cdx` is only taken for FoxPro 2 when the `.cdx` opens and its tags name only the table's fields; otherwise it stays dBASE IV and the missing `.mdx` keeps blocking writes.

## [0.1.0] - 2026-10-31

The first public release.

### Engine (Thunder.Dbf)

- **Tables:** read and write dBASE III, dBASE IV, FoxPro 2 and Visual FoxPro tables, including Visual FoxPro integer, currency, double and datetime fields, null flags and autoincrement counters.
- **Memos:** dBASE III and IV `.dbt` and FoxPro `.fpt` files, preserving dBASE IV free-block chains and FoxPro block types.
- **dBASE IV `.mdx` indexes:** read and seek, and kept exact on every append, update, delete and recall (unique tags, `FOR` filters, node splits, free pages), plus `RebuildIndex()`.
- **Other indexes:**
  - Read and seek dBASE III `.ndx`, Clipper `.ntx` and FoxPro `.cdx`/`.idx`, all through `IDbfIndexTag`.
  - Keep `.ndx` and `.ntx` up to date on every write, `.ntx` under Clipper's own index lock.
  - FoxPro `.cdx`/`.idx` maintenance is an opt-in preview (`MaintainFoxProIndexes`).
- **Which indexes are kept:**
  - An index is kept only when it is surely the table's: the header names it, or it's named after the table, or `MaintainIndex(path)` names it.
  - National sort orders, Clipper custom/changes-only indexes and over-wide numeric keys are refused rather than guessed at.
  - After a failed index update, writes stop until `RebuildIndex()`.
- **FoxPro 2 tables** that share dBASE's version byte are recognized by their `.cdx`.
- **Expressions:** a dBASE evaluator for key and `FOR` expressions (`UPPER`, `SUBSTR`, `DTOS`, `STR`, `VAL`, `IIF`, `DELETED()` and more), with three-valued `.NULL.` logic.
- **Locking:** record, header, append and table locks at dBASE, Clipper or Visual FoxPro offsets (`LockScheme`), shared across every table opened in one process; `LockRecord`/`LockTable`; `Refresh()` to see other programs' changes.
- **`UpdateFields`:** changes only the named fields, re-reading the record under its lock, so concurrent edits to other fields survive.
- **Typed records and LINQ:**
  - `ReadAll<T>`, `Read<T>`, `AppendRecord` and `UpdateRecord` map records to plain C# classes.
  - `AsQueryable<T>()` turns an equality on an indexed field into a seek, but only when the seek must give the same answer as a scan.
  - `Explain()` shows which plan a query uses.
- **`INDEX ON` and `PACK`:**
  - `CreateIndexTag` adds `.mdx` tags, creating the file when needed, laid out as dBASE software writes them.
  - `Pack` removes deleted records and rebuilds every index, keeping a safety copy until it's done.
- **Connecting:** one-line `DbfDatabase.Open` from a folder or a connection string, read-only by default; a `Check()` handshake; links and path tricks refused.
- **Errors:** `DbfException` with codes, safe messages, hints, HTTP statuses, and diagnostics kept separate for logs.
- **CSV:** import with the column shape worked out from the data, streamed in two passes; spreadsheet-safe export.
- **ADO.NET provider:** `DbfConnection`, `DbfCommand`, `DbfDataReader`, with index-assisted lookups, `CommandTimeout` and `Cancel()`, top-N sorts, and limits on statement size and nesting.
- **Code pages:** over 60, including Mazovia.
- **Durability:** crash-safe commit order, and an `AppendRange` bulk load.

### SQL (Thunder.Dbf.Sql)

- `DbfMigrator`: copies tables to SQLite, SQL Server or PostgreSQL.
- `DbfBridge`: live two-way sync with conflict policies, in one serializable SQL transaction. Deletes follow the conflict policy, a retry after a failed commit doesn't append rows twice, and a packed table is refused rather than paired up wrongly.

### Web service (Thunder.Dbf.Server)

- A JSON API with hashed API keys, per-table and per-field permissions, schema validation, a two-line (intent, then done) write journal, consistent backups taken under the table lock, per-address and per-key rate limits, response-size budgets and OpenAPI.
- OpenID Connect sign-in beside API keys: bearer tokens from Entra ID, Auth0, Keycloak or any provider, checked by JwtBearer against the provider's keys and the configured audience. Roles, groups or any claim map, first match wins, to access profiles shaped like an API key's permissions; a token that maps to none gets 403. Users show up as `oidc:<sub>` in the journal, logs and rate limits. Sending a key and a token together is a 400.
- An OpenAPI schema per table: `GET /tables/{name}/openapi` and `GET /openapi/tables.json` add a `Table_<NAME>` component schema, typed from the DBF header, for each table the caller may read, without hidden fields. `/openapi/v1.json` stays generic and names no tables.

### Tools

- `thunder-dbf` command line: `check`, `info`, `import`, `export`, `migrate`.
- Samples, documentation, and a publish gate (editorial check, history check, CI on three operating systems, CodeQL, Dependabot, weekly maintenance).

### Packages and releases

- NuGet packages `Thunder.Dbf` and `Thunder.Dbf.Sql`, with XML docs for every public member, Source Link, deterministic builds and `.snupkg` symbols; `thunder-dbf` as a .NET global tool (`dotnet tool install -g thunder-dbf`).
- The web service as self-contained zips for Windows (x64), Linux (x64) and macOS (Apple silicon) on each GitHub release.
- A release workflow triggered by `vX.Y.Z` tags: checks the tag against the version and changelog, tests, packs, publishes to nuget.org with trusted publishing (no stored API key) and creates the GitHub release with checksums. CI packs and checks the packages on every pull request.
